# 数据库网络断连演练复盘

2026-10-05 的 v5 本地合成演练实际中断了 13 条既有数据库转发连接，并验证新 libpq 连接被拒绝。两个 API 实例的 ready 检查和已预热上下文取用均返回 503，取用响应只包含固定的 `DATABASE_UNAVAILABLE` 错误码，没有正文。连接恢复后，双实例权限、幂等与业务安全烟测通过，原数据库路由恢复。演练报告为 `runtime_passed=true`，单调时钟计量的全流程时长为 254.024 秒。

这是项目实施者 cloudwallker 执行的本地合成故障实验。故障由演练工具主动注入，定位、原因确认与修复也由工具自动执行；没有真实用户事故、人工接警、值班团队或生产恢复记录。本复盘限定于数据库网络场景；已完成的坏版本回滚和新卷恢复分别见[运行证据](runtime-evidence.md)，36 项正式容量矩阵与 9 项对照列为后续验证。

## 背景与演练前固定目标

两个 API 实例共享一个 PostgreSQL，各有独立正文缓存。缓存不保存准入决定，每次取用仍需在主库检查当前权限、来源版本与有效期。因此本次预期行为是数据库断连时拒绝取用，即使正文已在缓存中，也不能凭旧状态放行。实现边界见[架构说明](../architecture.md#缓存与故障)。

演练在本项目的 Linux Docker Compose 环境中执行，使用项目专属 TCP 故障代理临时承接两 API 和 PG exporter 的数据库路径。注入前记录了代理就绪、两 API 就绪、HAProxy 后端正常，以及两次基线取用成功。实验只覆盖项目内部数据库网络路径；数据库进程没有被本场景主动停止。

## 原因与放大因素

**直接原因是项目专属故障代理执行 cut。** 代理关闭既有双向 socket 并拒绝新转发，两 API 无法在主库确认当前准入条件。旧连接关闭数量与新连接失败的双重证据，将本次原因限定为主动注入的数据库网络路径阻断，而不是把任意探测失败都当作数据库网络故障。脚本只有在 libpq 客户端确实启动、完成且返回预期失败退出码时才记录原因确认。

**共享数据库依赖扩大了影响范围。** 两实例同时依赖该主库，正文缓存不能保存放行结果；另一实例也不能继续正常取用。这是当前单主库设计的可用性边界。缓存在故障时拒绝返回正文达到了安全目标，同时产生预期的业务不可用。

**连接池等待和监控依赖延长了观察过程。** 已保存的样本出现 pending 和 timeout；数据库聚合采样也经过被切断的路径。代理准备与原路由恢复需要重建 JVM，指标序列在重建期间暂时缺失，累计计数在新 JVM 中重置。不能把末尾 timeout 计数回到零当作历史超时被消除，也不能用缺失样本推定故障期间资源稳定。

本次没有证据证明数据库进程崩溃、主机磁盘损坏、生产网络分区、真实权限错误或数据丢失。已读 PG 样本中未发现锁等待，故障期间又有采样缺口，因此不把锁等待的零值外推到整个窗口。

## 有效操作、失败尝试与无效判断

有效操作包括：在切断前确认 HAProxy 后端基线；同时验证旧连接和新连接；直接请求两实例检查预热缓存的拒绝契约；按实际 webhook 接收时间验证告警；恢复后重做双实例安全烟测；清理时恢复原路由并再次验收。它们分别避免了把启动未收敛、客户端缺失、单实例正常或仅监控恢复误判为完整结果。

## 证据保留与结论限制

原始证据在 `.gitignore` 排除的本地目录保留，未作为公开仓库文件发布：主报告 `artifacts/local/fault-db-network-v5.json`；七时点及实际 Prometheus 样本 `artifacts/local/fault-db-network-v5-timeline.json`；资源采样 `artifacts/local/fault-db-network-v5.resources.jsonl`；历史 v1–v4 对应同目录报告；告警交付 `.local/alerts/alerts.jsonl`。本文件是脱敏后的公开摘要，只使用必要合成统计、固定结果与相对证据路径，不包含正文、来源或上下文真实 ID、令牌、原始命令环境、私有主机路径或完整标签转储。

v5 的 24 行资源记录保留了 **10 次采样错误**：5 次 `service_observation_failed` 和 5 次 `metric_observation_failed`，客户端采样失败为 0。前者发生于 02:23:06.029024、02:23:17.569962、02:23:29.714154、02:23:40.663879 和 02:24:59.726628 UTC；后者发生于 02:22:22.430451、02:22:33.832817、02:22:45.131795、02:25:08.521201 和 02:25:19.914883 UTC。错误覆盖了注入前和原路由重建阶段，不能全部归为数据库断连窗口内的预期缺失。`sampling_failure_during_injected_outage_is_retained=true` 表示保留失败的策略，不证明每一次失败都由注入造成。

当前证据支持“真实数据库网络路径中断时，两实例已预热取用保持拒绝；主要告警实际交付；连接修复后安全验收并恢复原路由”。它不证明持续流量下的失败率与尾延迟、无缺口资源曲线、人工值班响应、数据卷恢复 RPO/RTO、宿主机损毁恢复、多机高可用或异地容灾。两个 API、HAProxy、单主库和宿主机的单点边界保持可见；坏版本完整回滚与新卷数据库恢复使用各自已留存的实际报告，正式容量矩阵仍属后续验证。
