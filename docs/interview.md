# 面试讲解

## 一分钟介绍

“我做了一个 Java 上下文失效控制服务。业务系统把来源片段和它生成的摘要交给服务管理。每次送给 Agent 使用之前，服务检查当前来源版本、权限和有效期。撤权提交后，即使另一台机器缓存着摘要，也不能再次取出。项目包含两个 JVM、真实 PostgreSQL 锁竞争、网络中断和进程终止实验。”

随后直接运行 `scripts/demo.py`，展示撤权前读取、撤权后 50 个新请求拒绝、旧上下文在重新授权后仍失效。展示 `docs/reports/report.html` 中实际状态计数，不把本机延迟包装成生产 QPS。

## 需要讲清的工程问题

**为什么两个版本？** 正文版本回答“资料是否变了”；授权 epoch 回答“授权历史是否改变”。只检查当前 ACL 会让撤权再授权后的旧上下文复活。epoch 把旧授权时刻和新授权时刻分开。源级 epoch 会让仍获授权的其他用户也失效，是保守选择。

**为什么缓存广播不够？** 通知可能延迟、丢失、进程暂停。正文可以缓存，准入决定每次向主库确认。代价是数据库读依赖和可用性：主库不可达时宁可返回 503。缓存并不是权限事实来源。

**如何避免检查后被撤权？** 读持有租户共享锁，写持有同一行的排他锁。锁内完成状态检查、正文复制和决策写入，提交后才交给 HTTP。READ COMMITTED 必须在拿到锁后再执行新查询，否则可能使用过时快照。锁后取 `clock_timestamp()`，避免 `now()` 冻结在事务开始导致等锁过期仍放行。

**为什么拒绝不直接抛异常？** 事务内抛异常会回滚拒绝记录。策略拒绝返回一个没有正文的决策值，事务提交后 HTTP 层按该值选择 403/409/410/503。

**为什么不遍历所有后代？** 每个派生项保存服务端合并的叶子来源及绑定版本。源变化后，下一次取用直接与当前状态比对。无需异步修改成千上万个后代，但会增加依赖集合存储，首版限制为 32 个来源和 4 层深度。

**幂等如何处理未知结果？** 来源事件完整快照与结果在一个事务中写入，事件唯一键为 tenant/source/sequence。提交前终止不会半写；提交后响应丢失时，相同快照重放返回已保存结果。同序号异参不能当成功重试，返回冲突。

## 不应作出的承诺

- 不能撤回已经送到客户端或模型的数据。先获得共享锁的重叠读可以完成，其响应甚至可能晚于撤权确认到达。
- 不能识别未登记的真实语义依赖。producer 是受信角色；文本是不是从那些父项生成，要由生产者集成保证。
- 不能发现尚未同步的上游变化。五分钟新鲜度只是限制已知状态的年龄，连接器必须可靠刷新完整状态。
- 逻辑删除不等于物理擦除；数据库、内存和备份可能仍有内容。
- 不是生产级 IAM 平台，也未证明高吞吐。租户级写锁、有界逐项查询和单主库都是首版取舍。

## 可以继续发展的方向

先测同租户读写分布和 guard 等待，再决定是否采用有序源级锁；多个来源必须遵循固定锁顺序。接入 OIDC 需要验证可信租户/主体映射和 token 生命周期。真实资料连接器需要把权限变化与资料版本同步为完整、可重放快照。只有需求明确时再加保留/擦除策略、流量限制和来源刷新运维面板。

这些是后续设计题，本项目没有把它们写成已经完成的功能。
